# Firmware formats

PIHC is a HiChip update container. Member names may use any portable printable-ASCII relative path; each member is accepted only with its CRC32, exact size and exact stream end. Its fixed header points to a pre-archive segment and a modified ZIP region. The SSC338Q fixture has a SquashFS/XZ pre-archive segment and 493 independently verified update members. There are 344 original CRC matches and 149 matches after AES/XOR restoration. Its central-directory audit reports malformed metadata.

The PIHC reader requires a bounded archive offset from the 512-byte header and scans local records in the archive range. It tries each original payload first. Automatic recovery probes the supported phase and rotation combinations on a bounded sample of failed members. A transformed member is admitted only after its own size and CRC checks pass. Source ranges are relative to the original package. Strict recovery requires all eligible members to pass.

Standalone classic ZIP accepts stored and raw DEFLATE members with consistent central and local records. If general-purpose bit 3 is set, the next local record or the start of the central directory bounds the descriptor. The parser checks the descriptor's sizes and CRC against the central record. It accepts classic 32-bit descriptors with or without the signature. Encrypted entries, ZIP64, split archives and special nodes are outside this subset. Directory entries contribute to the structural audit. [ZIP APPNOTE](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT)

Structure and extraction are judged separately. If the end, central and local records agree, candidate discovery proves the archive's extent even when a member uses LZMA or bzip2, carries a non-ASCII or unsafe name, repeats a name or is a link. Recovery then refuses the archive as unsupported rather than damaged. ZIP64 fields, including the 64-bit data descriptors that Info-ZIP writes when streaming, are rejected under their own check, `zip_classic_32bit_records`.

The TAR reader accepts POSIX USTAR and GNU-format headers for regular files and directories. It checks octal sizes, header checksums, path collisions, padding and the two-block end marker. It indexes the first archive and preserves any trailing data in the original. Members are copied from exact source ranges under `recovered/unverified/tar/`. The header checksum covers metadata. Member SHA-256 records the bytes copied from the source. Links, devices, PAX extensions, GNU long-name records and sparse records are outside this subset. So are repeated or case-aliasing member names: an update wrapper that stores `header` and `trailer` twice is a valid TAR, but its members cannot be copied to separate portable paths. Candidate discovery still records independently recognized structures inside the TAR payloads.

SquashFS 4.0 support includes a bounded superblock inspection and a walk of the inode and directory metadata block chains. Linux sandbox extraction can inventory a single validated image. Legacy uImage checks both CRCs and carves the stored payload with its exact source range. ELF inspection supplies static metadata and optional Ghidra analysis.

Raw NAND layouts, UBI/UBIFS extraction and partition-table reconstruction are outside the current format subset. Candidate discovery can carve a structurally validated FDT and report UBI erase-counter or XZ stream headers with unknown extents. bzip2, zstd and big-endian SquashFS findings remain signature-only. Unknown bytes and failed structure checks can be preserved with `--allow-partial`. A resource limit on valid input, for example a gzip member that decodes beyond the entry limit, is preserved the same way and reported as an exhausted budget. Board identity, vendor authenticity and flash coverage require independent evidence. [Candidate discovery](candidates.md)

`scan` classifies a rejected outer format as `structure_check_failed` (damage), `unsupported` (valid but outside the supported subset), `resource_limit` or `read_error`.

Single-member gzip supports bounded DEFLATE decoding with CRC32 and ISIZE trailer checks. Header metadata is bounded and never supplies output paths. Trailing data and concatenated members are rejected. The decoded image is published as `recovered/images/gzip-payload.bin`.
